# Security

Machine-readable contact details: [`/.well-known/security.txt`](https://5a8er.ir/.well-known/security.txt) (RFC 9116).

## Reporting a vulnerability

Report privately to the address in `security.txt`. Please include reproduction
steps and, where relevant, the request/response pair. I will acknowledge
receipt within 72 hours.

Testing that is in scope: `5a8er.ir`, `cf.5a8er.ir`, `admin.5a8er.ir`. Out of
scope: denial of service, volumetric testing, social engineering, and reports
generated by an automated scanner with no manual verification.

## Posture

This site is a portfolio, so its own configuration is part of what it claims.
The intent is that a reader can verify these statements with `curl` rather than
take them on trust.

### Transport and headers

Every response carries a strict Content Security Policy built around a
per-request nonce:

```
default-src 'none';
script-src 'nonce-{random}' 'strict-dynamic' https:;
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self';
connect-src 'self' https://challenges.cloudflare.com;
frame-src https://challenges.cloudflare.com;
base-uri 'none';
form-action 'self';
frame-ancestors 'none';
object-src 'none';
upgrade-insecure-requests
```

Alongside it: `Strict-Transport-Security` with preload, `X-Content-Type-Options:
nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options:
DENY`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy:
same-origin`, and a `Permissions-Policy` denying camera, microphone,
geolocation, payment, and USB.

Verify with `scripts/verify-headers.sh`, which asserts the header set is
identical across the apex and both origins.

### A recommendation deliberately declined

Lighthouse and Google's CSP Evaluator both suggest adding `'unsafe-inline'` to
`script-src` for backward compatibility. The advice is technically sound: any
browser that understands nonces ignores `'unsafe-inline'` entirely, so it
weakens nothing modern and helps browsers old enough to ignore nonces.

It is declined here anyway. The argument this site makes is that you can check
its claims with `curl`, and a reader who greps the policy and finds
`'unsafe-inline'` in `script-src` has to already know why it is inert before it
reads as anything but a contradiction. The browsers it would help predate the
audience. `https:` is already present as the fallback for browsers that ignore
`'strict-dynamic'`, which covers the realistic range.

### Two things this does not do

Stating them plainly is more useful than a policy that quietly overstates
itself.

**The nonce costs static rendering.** A nonce must be unique per response, so
pages cannot be served as cached HTML. Static assets still cache immutably and
TTFB is edge-render time in the tens of milliseconds, but there is no full-page
CDN cache. That trade was made deliberately: `script-src 'unsafe-inline'` is
not a defensible header to serve from a site that argues for application
security.

**`style-src` still allows `'unsafe-inline'`.** Next.js and Tailwind emit inline
style attributes during hydration. This is tightenable with hashes and has not
been done yet. Inline styles are a materially smaller risk than inline scripts,
but it is a gap, not a decision.

### Content pipeline

Blog posts are authored through Keystatic and stored as Markdoc in the
repository. Markdoc is a data-driven renderer with an explicit tag allowlist
and no code execution, unlike MDX, which compiles arbitrary JSX from content
files. Content is compiled at build time; nothing in the request path parses
untrusted markup.

### Contact endpoint

`POST /api/contact` applies, in order: Turnstile verification, a hidden-field
honeypot, a minimum dwell-time check, schema validation with Zod against a
schema shared with the client, and a sliding-window rate limit backed by
Upstash Redis.

The rate limiter is deliberately *not* in process memory. The site runs on two
independent origins, so a per-process counter would grant an attacker double
the quota simply by alternating between them.

Responses are generic — `200`, `400`, or `429` — and never reflect submitted
input. Message bodies are not logged.

### Administrative surface

The Keystatic admin exists in exactly one deployment. It is excluded from the
Cloudflare build at compile time via `pageExtensions` in `next.config.ts`, so
those routes are not merely unreachable there, they are not present in the
bundle. The single instance sits behind Cloudflare Access in front of GitHub
OAuth.

### Failover

The apex is served by a Worker that fails over to a second origin. It retries
only `GET` and `HEAD`. A failed `POST /api/contact` is surfaced to the caller
rather than retried, because a blind retry would send the message twice and
consume the rate-limit budget twice.
